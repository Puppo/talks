# AGENTS.md — Repository Onboarding

> **Read this first** if you are an AI coding agent working on this repository.

This file is intentionally placed at the repository root so it is automatically picked up by OpenCode, Claude Code, Cursor, Codex, and any other tool that looks for an `AGENTS.md` markdown file at the git root.

## What this repository is

This is the source for **Luca Del Puppo's public tech talks**, hosted at <https://talks.delpuppo.net> and published to Netlify. Each talk is a self-contained folder of static slide decks generated by [Freya](https://github.com/perseveranza-pets/freya) and rendered with Preact + TypeScript + SWC.

There is **one folder per talk** in `src/talks/<slug>/` containing `info.yml`, `slides.yml`, `talk.css`, and an `assets/` directory. The visual layer (layouts, theme, fonts, icons) lives in `src/themes/main/` and stays stable across all talks.

The goal of this document is to give an agent everything needed to add a new talk or review an existing one without breaking the visual or editorial style.

## Skills

Specialized workflows live under `skills/` (one folder per skill, with a `SKILL.md`). Read the matching skill before doing one of these tasks:

- **Adding or scaffolding a talk** — `skills/build-talk/SKILL.md`
- **Reviewing an existing talk** (report-only) — `skills/review-talk/SKILL.md`

Every skill follows the standard `name` + `description` frontmatter so any agent that ships a skills catalog can pick them up automatically.

## Adding a talk (short)

1. Read `skills/build-talk/SKILL.md`.
2. Pick a kebab-case slug unique under `src/talks/`.
3. Scaffold files from the skill's template, which mirrors `__master/slides.yml`.
4. Run `npm run lint -- src/talks/<slug>` and `npm run typecheck`.
5. Run `npm run generate-cfp` to sync the CFP entry.
6. Preview with `npm run dev -- --only <slug>` and open `http://delpuppo.local:4200/<slug>`.

## Reviewing a talk (short)

Read `skills/review-talk/SKILL.md`, give it the slug (or `all`), and read the structured report. By default the skill **does not modify files** — it only reports.

## Conventions

These are not optional. They keep every talk consistent with the rest of the deck library.

### Naming

- Talk slugs are lowercase **kebab-case** (e.g. `vibe-coding-let-s-follow-the-flow`, never `vibe_coding` or `VibeCoding`).
- Asset filenames are lowercase with underscores (`developer_wall.webp`), referenced as `@talk/<file>`.
- The display title in `info.yml` is usually single-quoted because titles contain spaces and punctuation.

### `info.yml` shape

```yaml
---
config: common.config
document:
  title: 'Short talk title'
  titleFormatted: |
    Optional multi-line title
    for layouts that need a line break
  abstract: |
    One or two-paragraph abstract used on the CFP.
    Multi-paragraph abstracts use the `|` block scalar.
  author: common.author
  company: common.company
```

Always reference **`common.author`** and **`common.company`** rather than inlining those maps.

### `slides.yml` rules

- A **multi-document YAML stream** with one `---` separator before each slide. Do not add consecutive separators or a trailing separator that creates an empty document.
- The first three slides **must** be `layout: cover`, `layout: hello`, `layout: nearform` (in that order — every real talk follows this).
- The closing section must contain `layout: end`. It may be followed by resource/link slides, `layout: byebye`, an optional Questions slide using `layout: separator`, and a final `layout: cover` placeholder, as in existing decks.
- Use the `layout: breaker` layout sparingly as visual variety between long sections.
- All image references use the `@talk/...` or `@theme/...` aliases. Raw paths are forbidden.
- Code blocks must declare `code.language`.
- Sequence slides (`title: '… 1/3'`, `'2/3'`, …) must cover the full range with no gaps.
- Run `npm run lint` and `npm run typecheck` after every edit.

### Assets

- Commit only `.webp` files in the talk's `assets/` directory.
- Source JPG / PNG files live in `assets/__originals/` and are converted via `npm run convert-images`.
- Theme-level assets (logos, illustrations) are referenced as `@theme/<file>` and live under `src/themes/<theme>/assets/`.

### Editing the theme

- `src/themes/<theme>/` is the visual foundation. Treat changes there as a cross-cutting change requiring an explicit PR justification.
- New layouts must be added to `__master/slides.yml` so every talk has a documented example before they get used.

### `talk.css` conventions

- Prefix per-talk selectors with `.talk\@` (e.g. `.talk\@narrow-grid { row-gap: 0; }`). Native CSS nesting is fine for `&:hover`, `& > x`, `&.x`; Sass-style concatenation (`&__x`, `&--x`) is not supported.
- Most talks only need a handful of overrides — keep the file empty unless you actually need it.

## Quality gates

Before opening a PR or shipping:

1. `npm run lint` — must pass.
2. `npm run lint:css` — must pass.
3. `npm run typecheck` — must pass.
4. `npm run build` — must succeed.
5. For talk changes: run `npm run verify -- --only <slug>` to advance through the deck (optional but recommended for layout changes).

## Do / Don't

**Do**

- Read `src/talks/__master/slides.yml` before adding a new layout field.
- Reference shared values via `common.author`, `common.config`, `common.company`.
- Run `npm run lint` and `npm run typecheck` after every edit.
- Keep titles concise and **single-line** unless `titleFormatted` is intentionally multi-line.
- Use `@talk/…` / `@theme/…` aliases for assets.
- Regenerate the CFP via `npm run generate-cfp` after `info.yml` changes.

**Don't**

- Don't edit `themes/main/` casually — that's a cross-cutting change.
- Don't invent new layout names — add to `__master/slides.yml` first.
- Don't commit raw JPG / PNG files in `assets/` (use `__originals/` and run `npm run convert-images`).
- Don't add new npm scripts without discussion.
- Don't duplicate author / company info in `info.yml` — use `common.*`.
- Don't run `npm run dev` in the background — it is interactive.
